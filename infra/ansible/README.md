# infra/ansible

Configures the VMs created by [`../terraform/`](../terraform/): installs k3s (server on the
control plane, agents on the workers), sets the node labels for the simulated regions and taints
the control plane (P4), bootstraps ArgoCD and rolls out the ApplicationSets stage by stage. From
then on, [`../../gitops/`](../../gitops/) takes over the Kubernetes-side configuration.

## Versions

Deliberately pinned instead of following "latest"/"stable" tags (reproducibility – the P3
principle "no `:latest` tags" applied here as well). To update, change
[`inventory/group_vars/all.yml`](inventory/group_vars/all.yml):

| Component | Version | Source |
|---|---|---|
| k3s | `v1.37.0+k3s1` | [k3s-io/k3s releases](https://github.com/k3s-io/k3s/releases) |
| ArgoCD | `v3.4.5` | [argoproj/argo-cd releases](https://github.com/argoproj/argo-cd/releases) (latest stable version, not the 3.5 release candidates) |

## IPv6 (DHBWV6) and dual-stack

Despite its name, `DHBWV6` is **dual-stack**: in addition to its IPv6 address, every VM gets a
private but genuinely internet-routed IPv4 address via DHCP (see [`../terraform/`](../terraform/))
— originally wrongly assumed to be IPv6-only, disproved on a running cluster (the VMs reach
`github.com`, which has no `AAAA` record, over IPv4 without issues). IPv6 stays primary
everywhere; IPv4 is only added so that k3s can run dual-stack and pods (ArgoCD, external-dns) can
reach IPv4-only targets. For `roles/k3s_server` this means:

- `--node-ip`/`--cluster-cidr`/`--service-cidr` each get an `<IPv6>,<IPv4>` pair (IPv6 first);
  `--tls-san` gets both addresses as separate flags
- the IPv6 CIDRs stay in the ULA range `fd00::/8` (RFC 4193) instead of a globally routable block
  – pods/services do not need to be reachable from outside; the IPv4 CIDRs are k3s' own defaults
  (`10.42.0.0/16`/`10.43.0.0/16`) and do not collide with the VMs' own DHCP range `10.200.0.0/19`
- `--flannel-ipv6-masq`, so that IPv6 pod egress traffic is masqueraded behind the node address
  (ULA is not globally routable); k3s/Flannel masquerade IPv4 pod egress by default, no equivalent
  flag needed
- the local `kubeconfig` generated by k3s points at `127.0.0.1`/`[::1]` by default (IPv6 first in
  `--node-ip`, see above); after fetching it, `k3s_server` rewrites that to `https://[<ipv6>]:6443`
  (bracket syntax, otherwise the port colon collides with the address colons) — kubeconfig/SSH
  deliberately stay IPv6-only, only k3s itself runs dual-stack

## Structure

```
ansible/
├── ansible.cfg
├── secrets.yml.example       # template for secrets.yml (gitignored, see below)
├── inventory/
│   ├── group_vars/
│   │   └── all.yml          # pinned versions, IPv6/IPv4 CIDRs
│   ├── hosts.ini             # generated by Terraform, gitignored (see hosts.ini.example)
│   └── hosts.ini.example
├── playbooks/
│   ├── site.yml             # full run: common -> k3s_server -> k3s_agent -> node_labels -> argocd_bootstrap -> gitops_secrets -> gitops_rollout
│   └── bootstrap-gitops.yml # only argocd_bootstrap + gitops_secrets + gitops_rollout, can be re-run separately
└── roles/
    ├── common/               # package index, base packages, deterministic hostname, multipathd exclusion for Longhorn
    ├── k3s_server/           # k3s server (dual-stack flags), node token, fetch the kubeconfig locally
    ├── k3s_agent/            # k3s agent, join via token/URL of the control plane
    ├── node_labels/          # topology.ticketflow/region per worker + NoSchedule taint on the control plane
    ├── argocd_bootstrap/     # namespace, pinned manifest, admin password
    ├── gitops_secrets/       # ArgoCD repo credential + RFC2136 TSIG Kubernetes secrets (from secrets.yml)
    └── gitops_rollout/       # ApplicationSets in stages: apply platform, wait until all Synced/Healthy, then apps
```

## Why Ansible and not everything in Terraform (`user_data`/cloud-init)

Terraform models the *actual state of resources*; repeated configuration (e.g. rolling out k3s
again after a manual node reboot, or re-running only the `node_labels` role) is simpler and
idempotent with a dedicated configuration tool, without touching the Terraform state. This is also
the combination prescribed by the assignment (Terraform/OpenTofu + Ansible).

## Prerequisites

Ansible is not expected to be installed system-wide; it runs from a Python venv (on this
Debian/Ubuntu system the system Python lacks even `pip`, and `apt install` requires root
privileges that are not available without a password in the WSL setup — a venv needs neither).
Set it up once; the venv deliberately lives in the project root (`../../.venv`, already in
`.gitignore` there), not under `infra/ansible/`, so that other tools (Terraform helpers, Python
scripts) can share it project-wide:

```bash
cd /path/to/repo-root          # DHBWCASCloudNative/
python3 -m venv .venv
source .venv/bin/activate
pip install -r infra/ansible/requirements.txt
```

Activate it before every Ansible call (`ansible-playbook`, `ansible-lint`, `ansible-inventory`, ...):

```bash
source /path/to/repo-root/.venv/bin/activate
```

Like k3s/ArgoCD, `ansible-core`/`ansible-lint` are deliberately version-pinned
([`requirements.txt`](requirements.txt)); to update, change them there instead of running
`pip install -U` without a pin. This only applies to the Ansible control machine (WSL/Linux, see
the root `CLAUDE.md`) — nothing Python-related is required on the managed VMs themselves except
the system Python that cloud images ship anyway, which Ansible talks to over SSH.

## Usage

```bash
cd infra/ansible
ansible-playbook playbooks/site.yml
```

Afterwards:

```bash
export KUBECONFIG=infra/ansible/kubeconfig
kubectl get nodes -o wide          # 4 nodes, workers labeled topology.ticketflow/region
kubectl -n argocd get pods         # ArgoCD is running
kubectl -n argocd get applications -L ticketflow.io/stage   # 21 Applications, all Synced/Healthy
```

The ArgoCD admin password is printed in the console output at the end of the playbook run
(`argocd_bootstrap` → task "Show the initial admin password").

## GitOps secrets (`gitops_secrets`)

Two things GitOps structurally cannot provide itself (ArgoCD is git-driven, and per `CLAUDE.md`
## Infra layering both values must **not** be in the git repo): the ArgoCD repository credential
for the private GitHub repo itself, and the RFC2136 TSIG Kubernetes secrets that
`charts/cert-manager-config`/`charts/external-dns` reference. The `gitops_secrets` role closes
both gaps, but runs entirely locally against the fetched `kubeconfig` (no SSH, the secrets never
end up in a process list on the VMs) and installs no Helm charts/operators itself — that stays
entirely GitOps-owned.

**Repo credential (SSH deploy key, once):**

```bash
cd infra/ansible
ssh-keygen -t ed25519 -C "argocd-deploy-key@ticketflow" -f argocd_deploy_key -N ""
cat argocd_deploy_key.pub
```

Add the printed public key under GitHub → repo → Settings → Deploy keys → "Add deploy key" as a
**read-only** key. `argocd_deploy_key`/`argocd_deploy_key.pub` are gitignored. Every `Application`
generated by `gitops/applicationsets/` points at a chart in this repo (see `gitops/README.md`
## Struktur) and therefore uses `repoURL: git@github.com:...` (SSH) instead of `https://...` — only
the upstream Helm repos that the wrapper charts reference in their `Chart.yaml.dependencies`
(Longhorn, cert-manager, external-dns, ...) stay plain public HTTPS and need no credential.

The role no longer reads the repo URL from a hard-wired literal but via `include_vars` from
`gitops/env/cluster.yaml` (`ticketflow.repoURL`) — the same file ArgoCD and all charts read their
values from. It used to be a literal here and was therefore the one place a fork reliably missed:
the credential was then registered for the **original** repo, and all Applications stayed
`Unknown` forever without the error message pointing at the cause.

**RFC2136 TSIG (once the DNS zone is active):**

```bash
cp infra/ansible/secrets.yml.example infra/ansible/secrets.yml
# fill in rfc2136_tsig_secret_value in secrets.yml (the file is gitignored)
```

Then apply both:

```bash
ansible-playbook playbooks/site.yml                    # or specifically:
ansible-playbook playbooks/bootstrap-gitops.yml         # only ArgoCD + gitops_secrets + gitops_rollout again
```

If `argocd_deploy_key` or `secrets.yml` is missing (or the latter still contains the placeholder
`CHANGE_ME`), the respective part of the role skips itself instead of failing — see
`gitops/README.md` ## DNS/ACME for the DNS part of the overall picture. Note that without the repo
credential the platform stage of `gitops_rollout` can never turn green.

## Open points

- No own ingress/load-balancer handling: k3s installs Traefik and ServiceLB by default; the
  charts use them (Traefik is configured via `charts/traefik-config`).
- `become` requires passwordless `sudo` for the SSH user configured in `hosts.ini` – on the usual
  cloud images (e.g. Ubuntu cloud images with a prepared `ubuntu` user) that is the default.
- `ansible-lint` (profile `basic`) still reports purely stylistic findings (FQCN module names such
  as `command` instead of `ansible.builtin.command`, `no-role-prefix` on `register` variables,
  missing `changed_when` on the gated install shells) – none of them changes behavior; deliberately
  not fixed to keep the diff small. New roles (e.g. `gitops_secrets`) are kept
  `risky-shell-pipe`-clean (`set -o pipefail`, see the CLAUDE.md note on the `curl | sh` bug).
  Re-run `ansible-lint` to see the current list if needed.
